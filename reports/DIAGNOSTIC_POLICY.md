## Observed gaps at the reviewed base

- `eval.metrics.pilot_task_set` and driver help used the historical 50-task cap.
  Selection was already deterministic and occurred before task execution.
- Driver sampling defaulted to `pilot_10pct`, with three improvement rounds;
  there was no separate one-task diagnostic or required diagnostic review.
  `trials` and `jobs` already defaulted to 1, but larger values were accepted.
- The runner excluded its `invalid` results and scorer `unmeasured` verdicts
  from `per_task`. It combined these failures under `invalid`, while curve
  points exposed only invalid counts and selected/scored information.
  Some runtime failures retained scored zeros under the general runner contract.
- Driver reused run directories with `exist_ok=True`. An incomplete receipt
  could be mixed with a later attempt using the same ID.
- There was no staged receipt schema covering provenance, metric identity,
  full task/trial coverage, lifecycle evidence, and expansion review.

## Implemented behavior

- Default staged sampling is now `diagnostic`: one stable task chosen from the
  eligible side/subset before runtime admission. `pilot_10pct` selects
  `min(30, ceil(0.10 * unique_eligible))` tasks. Empty pools select zero tasks and
  are refused by the driver. Both stages enforce `trials=1`, `jobs=1`, and
  `rounds=0`; the driver disables the improver for these measurements.
- Staged runs require `--policy-evidence`. Its `context` binds dataset/side,
  metric/scorer hash, source/split/manifest/model/harness SHA256 values, one
  configured local GPU endpoint, resource/budget limits, comparability notes,
  and passing dataset gate evidence. Unknown facts use explicit null values.
  The driver checks the configured endpoint and requires a live model backend.
- `pilot_10pct` additionally requires a `receipt` and separate `review` in the
  evidence object. The diagnostic must have exactly one measured trial, no
  invalid/unmeasured outcomes, passing gate/cleanup/snapshot evidence, known
  provenance/limits, and matching context. Review requires an approving reviewer,
  a review-time field, and the exact canonical SHA256 of the diagnostic receipt.
  The full eligible ID pool is hash-bound, so same-sized pool changes are refused.
- Staged IDs reserve a new directory exclusively; autogenerated IDs include a
  random suffix. Existing directories, traversal IDs, and reuse of the reviewed
  diagnostic's explicit ID are refused. Existing receipts are never overwritten.
- The driver preserves `staged_plan.json` before runtime preparation, with
  expected coverage and explicit unmeasured outcomes. After evaluation, both
  train and eval paths write `diagnostic_receipt.json` before result refusal.
  Invalid/unmeasured/runtime-failed/cached outcomes carry null scores and reasons;
  such staged results cannot produce an ordinary curve point. A measured zero
  remains a valid zero and can pass diagnostic review.
- General explicitly selected sampling policies retain their previous behavior.
  Default improvement rounds for those policies remain 3.

## Reusable contract

`eval/diagnostic_policy.py` provides staged selection constraints, context and
lifecycle validation, runner-result adaptation, receipt construction/validation,
coverage summaries, eligible-pool hashes, canonical receipt hashes, review
validation, exclusive receipt creation, and fresh run-directory reservation.
It uses only the Python standard library and performs no model/runtime calls.

`eval/diagnostic_receipt.schema.json` declares
`harnessgrad.diagnostic-receipt.v2`. Each selected task has an explicit trial-1
outcome (`measured`, `invalid`, or `unmeasured`). Coverage records eligible and
selected tasks, expected trials, and measured/invalid/unmeasured task and trial
counts. `score` is the mean of measured outcomes, or null when none exist; a
partial mean is never a complete diagnostic authorization. The Python validator
checks coverage and score relationships beyond the JSON schema's shape checks.

Version 2 adds an explicit `lifecycle` checkpoint (or null). Measured outcomes
require the shared `scope → admit → execute → quiesce → score → seal → cleanup`
sequence to pass, including completed snapshot/export and exact cleanup absence
evidence. Pending/failed lifecycle evidence withholds both aggregate and task
scores as unmeasured/null; existing invalid outcomes remain invalid.

The schema and Python validator allow unknown provenance/lifecycle evidence to
preserve incomplete receipts. `require_review` rejects unknown evidence for
expansion. `write_receipt` uses exclusive creation, so trusted orchestration must
write later attested evidence under a new filename and review its exact hash.
Historical v1 files are preserved and are not accepted as v2 expansion evidence.
The driver supplies no trusted lifecycle observations and therefore cannot publish
a staged measured curve. No synthetic observer is installed in production.
See [the lifecycle review](lifecycle-codex177-report.md) for the contract and limits.

## Remaining boundaries

- Receipt validation establishes structural consistency, not the authenticity
  of supplied gate/reviewer attestations or independently verified source/model
  provenance. The trusted orchestrator must supply and verify those artifacts.
- Driver-generated cleanup and snapshot attestations remain `unknown`, because
  the current driver does not provide verified lifecycle receipts. A measured
  diagnostic from this driver alone therefore cannot authorize expansion.
- Resource/budget fields are recorded and compared; this policy does not add
  filesystem quota enforcement or global H0 concurrency accounting. Existing
  trusted runtime/budget admission must enforce those limits.
- Dataset loaders still materialize their existing task/environment tables before
  narrowing; this patch does not establish selected-only loading or offline
  scorer/runtime closure. Those remain independent production admission gates.
- No scientific results or valid production diagnostic receipts were obtained
  during this task. Nothing here authorizes a larger pilot or method tuning.
